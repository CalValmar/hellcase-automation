# AGENTS.md

- This repo is one production script plus offline tests in `tests/`. Run it with `python3 daily_reward.py` (Python 3.6+ for f-strings); data paths are absolute, so the working directory does not matter. Verify from the repo root with `python3 -m unittest discover -s tests -t . -v`; the tests use a fake API and never call Hellcase.
- Local state lives outside the checkout: `~/.config/hellcase-automation/config.json` (`discord_webhook_url` + `accounts` array of `{username, xsrf, session}`), and `~/.local/state/hellcase-automation/{state.json,history.json,daily-reward.lock}` (`state.json` holds `last_claim`, `last_attempt_day`, `last_error_day` keyed by account index; `history.json` holds successful drops). Dirs are `700`, files `600`. `*.json.tmp` files are transient siblings. Local captures live in the gitignored `.captures/` folder: they contain `auth_code` and a Steam trade link. `config.example.json` is the only tracked template. `username` is a local label used in Discord/history, with no check against the API nickname. Empty/missing label falls back to `user.nickname`. Keep the `accounts` order stable: `state.json` keys by index. Back up the two home dirs, not the repository. On a server installed with `./setup.sh --system`, the service user is `hellcase`, `HOME=/var/lib/hellcase`, and the same config/state paths live under `/var/lib/hellcase/`.
- Each account gets its own `requests.session()` with its cookies. The `xsrf` token is sent both as the `XSRF-TOKEN` cookie and as the `X-CSRF-Token` header on the claim call. `hellcase_session` expires on logout or ~30 days; edit `~/.config/hellcase-automation/config.json` locally when calls start failing.
- The flow was identified from real captures and the site's own `useBoxService` JS: `POST https://api.hellcase.com/user_level/claim_free_case/newbie` returns `open_id`, then `GET https://api.hellcase.com/open/newbie/state` returns `bought` + `weapons[0]`. `GET https://api.hellcase.com/open/newbie` only returns the case page (no drop); it is kept for `user.nickname` and `casename`. Don't execute the script or start the timer as a test: a due account really claims its free case.
- A claim with `status` other than `success` or without `open_id` is a failure: the alert shows the API's `error_message` verbatim, or "raison inconnue" if absent. The real code `user_level.reward.already_claim` means "not due yet" and is silent and records `last_claim = now` so browser claims are not retried. Never guess "token expiré": the only verified auth signal is an API error message, and network/JSON failures say "réseau ou réponse inattendue". A state with `status` other than `success`, `bought` false, or no `weapons[0].item_name` is reported as "gain non renseigné par l'API". Failure alerts emitted after a successful claim include its `open_id` so the run is never replayed; failures write no history row, verified drops do. Raw responses are never logged.
- `extract_drop()` reads `weapons[0]` from the state response: `item_name`, `skin_name`, `steam_price_en` (fallback `item_price`), `rarity`, `steam_exterior`, `id`. The old `top_items` approach was a proven dead end — those entries are other players.
- Don't add endpoints that were not verified against the site JS or a real capture. `user.nickname` from `GET /open/newbie` is the only known source for the account label fallback.
- The API has no countdown field. `last_open_date` is not a reliable personal date: in one real capture it did not match the newest `top_items` entry. History uses the local run time instead.
- `~/.local/state/hellcase-automation/daily-reward.lock` + `fcntl` prevent two concurrent runs from opening the same cases. There is deliberately no `Restart=` in the service: a retry could reopen a case. Failures are notified on Discord instead.
- `systemd/daily-reward.timer` is shared by both modes (`OnCalendar=*-*-* *:00:00 UTC`, `RandomizedDelaySec=30m`, `Persistent=true`, `AccuracySec=1s`). `systemd/user/daily-reward.service` is the laptop unit (oneshot, 20min timeout; user-mode setup rewrites `ExecStart` to `$PWD/daily_reward.py`, no `WorkingDirectory`); `./setup.sh` installs both in `~/.config/systemd/user/` with `loginctl enable-linger $USER`. `systemd/system/daily-reward.service` is the LXC unit: `User=hellcase`, `Environment=HOME=/var/lib/hellcase`, a venv `ExecStart` at `/opt/hellcase-automation/.venv/bin/python`, and no `Restart=`. `./setup.sh --system` as root installs the shared timer and this service in `/etc/systemd/system/`. Never enable both types at once: remove the other mode's unit files (not just disable) before switching, and plain `./setup.sh` as root is refused. Both declare `After/Wants=network-online.target`, but it does not guarantee DNS, so the read-only `GET /open/newbie` is retried once on network errors or invalid JSON; never retry the claim.
- Hellcase calls have a 30s timeout (webhook 10s), at most 2 shuffled accounts are processed per run with a ~5 min delay between them, and webhook failures are ignored. A malformed account or unexpected JSON shape alerts once per UTC day and moves to the next account instead of aborting the run. A non-empty invalid `history.json` is renamed to `history.json.corrupt` and alerts once/day; empty files stay ignored. `setup.sh` rejects `xsrf`/`session` values starting with `REPLACE_`. `history.json.tmp` and `state.json.tmp` are chmod `600` before replace; `history.json` is written before `state.json` so a crash between them keeps the drop; a failed history write alerts with the `open_id` and continues to the next account. `state.json` skips accounts claimed within 24h + 1 min and limits a broken account to one attempt/day; `already_claim` is a normal silent skip. There is no `claim_available` gate: it was seen only `false` after a claim, so using it would risk missed cases.
