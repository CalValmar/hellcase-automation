# AGENTS.md

- This repo is one production script plus offline tests. Run it from the repo root: `python3 daily_reward.py` (Python 3.6+ for f-strings). Verify with `python3 -m unittest -v test_daily_reward`; the tests use a fake API and never call Hellcase.
- All local state lives in two gitignored files: `config.json` (`discord_webhook_url` + `accounts` array of `{username, xsrf, session}`) and `history.json` (successful drops). Both must be `chmod 600`. `daily-reward.lock` and `history.json.tmp` are transient local files, also gitignored. Local captures live in the gitignored `.captures/` folder: they contain `auth_code` and a Steam trade link. `config.example.json` is the only tracked template. `username` is a local label used in Discord/history, with no check against the API nickname. Empty/missing label falls back to `user.nickname`.
- Each account gets its own `requests.session()` with its cookies. The `xsrf` token is sent both as the `XSRF-TOKEN` cookie and as the `X-CSRF-Token` header on the claim call. `hellcase_session` expires on logout or ~30 days; edit `config.json` locally when calls start failing.
- The flow was identified from real captures and the site's own `useBoxService` JS: `POST https://api.hellcase.com/user_level/claim_free_case/newbie` returns `open_id`, then `GET https://api.hellcase.com/open/newbie/state` returns `bought` + `weapons[0]`. `GET https://api.hellcase.com/open/newbie` only returns the case page (no drop); it is kept for `user.nickname` and `casename`. Don't execute the script or start the timer as a test: every run claims the free case for every configured account.
- A claim with `status` other than `success` or without `open_id` is a failure: the alert shows the API's `error_message` verbatim, or "raison inconnue" if absent. The real code `user_level.reward.already_claim` means "not due yet" and is silent, since the timer checks four times a day. Never guess "token expiré": the only verified auth signal is an API error message, and network/JSON failures say "réseau ou réponse inattendue". A state with `status` other than `success`, `bought` false, or no `weapons[0].item_name` is reported as "gain non renseigné par l'API". Alerts emitted after a successful claim include its `open_id` so the run is never replayed. In every case no history row is written. Raw responses are never logged.
- `extract_drop()` reads `weapons[0]` from the state response: `item_name`, `skin_name`, `steam_price_en` (fallback `item_price`), `rarity`, `steam_exterior`, `id`. The old `top_items` approach was a proven dead end — those entries are other players.
- Don't add endpoints that were not verified against the site JS or a real capture. `user.nickname` from `GET /open/newbie` is the only known source for the account label fallback.
- The API has no countdown field. `last_open_date` is not a reliable personal date: in one real capture it did not match the newest `top_items` entry. History uses the local run time instead.
- `daily-reward.lock` + `fcntl` prevent two concurrent runs from opening the same cases. There is deliberately no `Restart=` in the service: a retry could reopen a case. Failures are notified on Discord instead.
- `systemd/` holds user unit templates: `daily-reward.service` (oneshot, 20min timeout; hardcoded `~/Documents/PERSO/Projets/hellcase-automation` paths) and `daily-reward.timer` (`OnCalendar=*-*-* 00,06,12,18:00:00 UTC`, `Persistent=true`, `AccuracySec=1s`). Install them in `~/.config/systemd/user/`; `sudo loginctl enable-linger $USER` is required to run while logged out. The unit declares `After/Wants=network-online.target`, but a user manager has no wait-online implementation, so the read-only `GET /open/newbie` is retried once; never retry the claim.
- Hellcase calls have a 30s timeout (webhook 10s), accounts are separated by a small random delay even after a failure, and webhook failures are ignored. A malformed account or unexpected JSON shape alerts and moves to the next account instead of aborting the run. `history.json.tmp` is chmod `600` before replace; a failed history write alerts with the `open_id` and continues to the next account. The 4 UTC check times absorb a rolling per-account cooldown without per-account timers; `already_claim` is a normal skip, not an alert.
